# 错误码表（W3）

> 所有接口的错误响应体形状统一为：

```json
{
  "code": "AUTH_401",
  "message": "登录已过期，请重新登录",
  "request_id": "3aca7e6dbef1",
  "detail": null
}
```

`request_id` 同时出现在响应头 `X-Request-Id` 和服务端日志中——
用户报错时抄一个 ID 过来，就能直接定位到那一次请求的全部日志。

---

## 码表

| code | HTTP | 含义 | 触发场景 | 前端怎么处理 |
|---|---|---|---|---|
| `OK` | 200 | 成功 | — | — |
| `VALIDATION_422` | 422 | 参数校验失败 | 邮箱格式错、密码太短、字段缺失 | 定位到 `detail[].field` 高亮输入框 |
| `AUTH_401` | 401 | 未认证 / 凭证无效 | 没带 token、token 过期、密码错误、refresh 无效 | 清 token → 跳登录页 |
| `AUTH_403` | 403 | 已认证但无权限 | 账号被禁用、越权访问他人资源 | 提示无权限，不要跳登录 |
| `NOT_FOUND_404` | 404 | 资源不存在 | 文档/会话 id 不存在 | 提示并返回列表 |
| `CONFLICT_409` | 409 | 资源冲突 | 邮箱已注册 | 提示"换个邮箱" |
| `RATE_429` | 429 | 触发限流 | 超过配额 | 提示稍后重试，展示倒计时 |
| `INTERNAL_500` | 500 | 服务端异常 | 未捕获异常 | 提示"稍后重试" + 展示 request_id |

---

## 设计说明

### 为什么不用 FastAPI 默认的 `{"detail": ...}`

默认格式有四个问题：

1. **不统一**：业务异常、校验异常、未捕获异常三种形状各不相同；
2. **没有错误码**：前端只能靠 HTTP 状态码分支，401 里分不清"没登录"和"过期了"；
3. **没有 request_id**：线上报错无法定位；
4. **可能泄露内部信息**：堆栈、SQL、文件路径会直接返回。

### 分层职责

| 层 | 该做什么 | 不该做什么 |
|---|---|---|
| `repos` | 只抛数据库异常 | 不翻译成业务错误 |
| `services` | 抛 `AppError(code, message, http_status)` | 不关心 HTTP 细节 |
| `routers` | 只做参数绑定 | 不写 try/except 业务异常 |
| `core/errors.py` | 统一翻译成响应体 | 不含业务逻辑 |

这样一来，新增接口时**不用写任何错误处理代码**，异常会自动变成标准响应。

### 一个安全细节

登录失败时，"邮箱不存在"和"密码错误"返回**完全相同**的 `AUTH_401` + "邮箱或密码错误"。
否则攻击者可以拿错误信息逐个试出哪些邮箱已注册（账号枚举）。

## 实测记录（2026-11-08）

| 场景 | 结果 |
|---|---|
| 未登录访问 `/api/auth/me` | `401 {"code":"AUTH_401","message":"未登录"}` |
| 无效 token | `401 {"code":"AUTH_401","message":"无效的登录凭证"}` |
| 重复注册 | `409 {"code":"CONFLICT_409","message":"该邮箱已注册"}` |
| 密码错误 | `401 {"code":"AUTH_401","message":"邮箱或密码错误"}` |
| 邮箱格式非法 | `422 {"code":"VALIDATION_422","detail":[{"field":"body.email",...}]}` |
| 密码太短 | `422 {"code":"VALIDATION_422","detail":[{"field":"body.password",...}]}` |
| 刷新令牌无效 | `401 {"code":"AUTH_401","message":"刷新令牌无效或已过期"}` |
