# W11 设计记录：向量化与混合检索

> 这周之后，问"文档里写了什么"终于能答上来了。
> 核心不是"用了个向量库"，而是**混合检索 + 约束引用 + 无答案拒答**这套组合。

## 一、链路

```
上传 → 解析 → 父子块 → 【子块向量化】→ ready
                                   │
提问 → 向量召回 top20 ─┐            │
     → 关键词召回 top20 ─┴→ RRF 融合 → top5 → 拼上下文（带编号）
                                            │
                                            ▼
                         模型只能依据资料回答，标注 [1][2]
                                            │
                         无资料 → 直接拒答（不调模型，省钱且不编）
```

---

## 二、为什么 embedding 用本地模型

| 方案 | 结论 |
|---|---|
| DeepSeek | ❌ 没有 `/embeddings` 接口（实测 404，模型列表只有对话模型） |
| 其他云 API | ✅ 但要额外注册 key |
| **本地 fastembed + bge-small-zh-v1.5** | ✅ 512 维，ONNX 运行时，内存约 200 MB，不需要 key |

选本地的三个理由：不需要额外 key、无网络依赖、ONNX 比 torch 轻一个数量级（服务器只有 1.7 GB）。

**代价**：512 维 small 模型，精度不如 bge-m3（1024 维）。
**换模型必须同步改 `chunk.embedding` 的列维度**（迁移 `c1d2e3f4a5b6` 就是干这个的），
否则插入会直接报类型错误。

## 三、为什么必须混合检索

向量擅长语义（"报销上限" ≈ "住宿标准"），但对**编号、金额、型号**几乎无效：
问 "LX-HR-2026-03" 或 "10000 元"，纯向量召回经常漏。

关键词反过来：字面命中准，但换个说法就废。

**RRF 融合**（不需要归一化分数，工程上最省事）：

```
score(d) = Σ 1 / (60 + rank_i(d))
```

中文没有分词器（zhparser 要编译），关键词召回用朴素做法：把问题按标点/空格切开，
每个长度 ≥ 2 的词做 `ILIKE`，命中词数作为排序依据。对金额、编号、专有名词够用。

## 四、四个关键决策

### 1. 只检索子块，命中后回填父块

子块 260 字检索更准；父块 1000 字给模型更完整。
W10 埋的父子块设计，这周兑现。

### 2. 引用编号由程序维护，不让模型写文档名

模型只输出 `[1][2]`，映射（文档名/页码/章节）存在 `message.citations` 里。
**让模型自己写页码它一定编**——这是引用溯源能不能信的分水岭。

### 3. 没检索到 → 直接拒答，不调模型

省一次调用，更重要的是**模型没有资料时一定会编**。
固定话术里还给出排查建议（没上传？换个说法？）。

### 4. 检索放线程池

向量化是 CPU 密集的同步调用，直接在 async 路由里跑会阻塞事件循环。
用 `asyncio.to_thread` 包一层。

## 八、面试怎么说

> "检索用了混合方案：pgvector 向量召回 + 关键词召回，RRF 融合后取 top5。
> 之所以必须混合，是我们测过纯向量对编号和金额几乎无效。
> 引用编号由程序维护、模型只输出 [1][2]，否则它会编页码。
> 检索不到时直接拒答——模型在没有资料时一定会编。"
