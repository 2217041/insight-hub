> 这一页读完，应该能回答 W7 自测题里的全部问题。

## 一、一次 chat 请求的完整链路

```
"你好" 
  → tokenizer(BPE) ─── 文本切成 token id
  → embedding ──────── id 变成向量
  → N 层 Transformer ── 每层：注意力 + FFN
  → 最后一层 ───────── 得到每个位置的 logits
  → 采样 ──────────── 温度 / top-p 决定选哪个 token
  → 解码 ──────────── id 变回文字
  → 循环 ──────────── 把新 token 接上去，重复
```

**关键认识**：模型一次只产出**一个** token。所谓"流式输出"，就是每算出一个 token 就推一段。

## 二、七个必须能讲清的概念

| 概念 | 要能说出的话 |
|---|---|
| **BPE 分词** | 不是按字也不是按词。中文常见 1 个字 ≈ 1 token，英文 1 词 ≈ 1.3 token；代码和罕见字更碎。**计费和上下文都按 token 算**，所以"字数"不等于"token 数"。 |
| **注意力** | Q·K 算相关度，加权求和 V。复杂度 O(n²)——**上下文翻倍，计算量变四倍**，这是长上下文贵的根本原因。 |
| **位置编码（RoPE）** | 注意力本身不知道顺序，位置编码把"第几个 token"注入进去。 |
| **KV Cache** | 生成第 n 个 token 时，前 n-1 个的 K/V 可以缓存复用，不用重算。**用显存换时间**。 |
| **prefill / decode** | prefill：一次性处理整段输入，**算力密集**（GPU 利用率高）；decode：一次一个 token，**带宽密集**（显存读写瓶颈）。所以并发高时吞吐上不去，瓶颈在 decode。 |
| **TTFT / TPOT** | TTFT = 首 token 延迟（用户"等待感"）；TPOT = 每 token 间隔（用户"流畅感"）。**首字慢最容易让人放弃**。 |
| **上下文窗口** | 能塞多少 token。塞满的代价：注意力平方级变慢 + 成本线性上升 + **中间信息容易丢**（lost in the middle）。 |

## 三、显存怎么算（面试高频，必须会）

### 公式

```
总显存 ≈ 权重 + KV Cache + 激活 + 框架开销
```

**权重**：

```
权重(GB) = 参数量(B) × 每参数字节数
  fp16 → 2 字节     int8 → 1 字节     int4 → 0.5 字节
```

**KV Cache**（这是最容易被忽略的部分）：

```
每 token 的 KV = 2 × 层数 × KV头数 × head_dim × 每元素字节
   （2 = K 和 V 各一份）

KV 总量 = 每 token KV × 序列长度 × batch_size
```

**框架开销**：CUDA context、cuBLAS workspace、tokenizer 等，通常再留 **10%–20%**。

### 估算表（以常见的 GQA 架构为例）

| 模型 | 层数 | KV头×head_dim | fp16 权重 | int8 | int4 | KV/1K token(batch=1) | 4090(24G) 能跑吗 |
|---|---|---|---|---|---|---|---|
| 7B | 28 | 4×128 | 14 GB | 7 GB | 3.5 GB | ~56 MB | ✅ fp16 轻松，可跑 8K+ 上下文 |
| 14B | 48 | 8×128 | 28 GB | 14 GB | 7 GB | ~192 MB | ✅ 只够 int4；fp16 放不下 |
| 32B | 64 | 8×128 | 64 GB | 32 GB | 16 GB | ~256 MB | ⚠️ int4 勉强（16G 权重 + KV + 开销） |
| 70B | 80 | 8×128 | 140 GB | 70 GB | 35 GB | ~320 MB | ❌ 至少 2×A100(80G) |

### 三个必须会的口算

**1. 7B fp16 要多少显存？**
权重 14 GB + KV（4K 上下文 ≈ 224 MB）+ 开销 ~1.5 GB ≈ **16 GB**。
所以 4090(24G) 跑 7B fp16 很宽裕，能留 8K 上下文。

**2. 4090 能跑 32B 吗？**
int4 权重 16 GB，剩 8 GB。每 1K 上下文 KV 约 256 MB → 最多约 24K token 上下文（还要留开销）。
**结论：勉强，但 batch 只能是 1，并发一上来就 OOM。**

**3. 70B 为什么必须多卡？**
140 GB 权重，单卡放不下 → 张量并行（TP=2 用 2 张 A100）。TP 每加一卡，通信开销也涨。

## 四、批处理（batch）为什么能提吞吐、不能降延迟

- 单请求 decode 时，GPU 大部分时间在**等显存带宽**，算力闲着；
- 把 8 个请求拼成一个 batch，一次矩阵乘法算 8 份 —— **算力利用率上去了，总吞吐变高**；
- 但每个请求要等整个 batch 算完，**单个请求的 TPOT 反而变长**。

这就是 vLLM 的 **continuous batching** 在解决的问题：不等整批结束，谁算完谁先走，
新请求随时插进来。PagedAttention 则是把 KV Cache 按页管理，减少显存碎片。

> 面试答法："batch 提升的是吞吐，牺牲的是单请求延迟；continuous batching 通过动态拼批，
> 让这个取舍没那么痛。"

## 五、采样参数怎么调

| 参数 | 作用 | 什么时候用 |
|---|---|---|
| `temperature` | 越高越随机 | 创意写作用 0.7–1.0；**抽取/分类必须 0** |
| `top_p` | 只在累积概率前 p 的候选里选 | 和温度二选一调，别同时大改 |
| `top_k` | 只在前 k 个候选里选 | 限制离谱 token |
| `frequency_penalty` | 抑制重复词 | 长文本生成时防复读 |

**注意**：温度设为 0 也**不保证**完全确定性——浮点运算顺序、并行规约都会带来微小差异。

## 六、微调 vs RAG vs Prompt

| 方案 | 解决什么 | 不适合 | 成本 |
|---|---|---|---|
| Prompt | 格式、角色、输出风格 | 注入新知识 | 最低 |
| **RAG** | **知识频繁更新、需要引用溯源** | 改变模型能力/语气 | 中（检索 + 上下文） |
| 微调（LoRA/SFT） | 固定格式、领域语气、蒸馏小模型 | 高频变动的知识 | 高（数据 + 算力 + 迭代） |

**一句话**：**知识用 RAG，能力/风格用微调，两者不冲突。**

本项目选 RAG，理由很具体：知识库天天变，而微调一次要重训、还要重跑评测。

## 七、自测（能全答出来才算过）

1. 7B 模型 fp16 权重占多少显存？为什么实际要更多？
2. KV Cache 缓存了什么？为什么用显存换时间？
3. TTFT 和 TPOT 分别受什么影响？用户先感知哪个？
4. 上下文从 4K 提到 32K，显存和延迟各自怎么变？
5. 温度设 0 能得到完全相同的输出吗？
6. 为什么 RAG 比微调更适合"知识频繁更新"？
7. LoRA 为什么能省显存？（提示：只训练低秩旁路，冻结原权重）
8. batch 变大后，吞吐和单请求延迟分别怎么变？

<details>
<summary>参考答案要点</summary>

1. 14 GB；还要加 KV Cache、激活、CUDA context 与框架开销，实际约 16 GB。
2. 缓存历史 token 的 K/V，避免重复计算；代价是显存随上下文线性增长。
3. TTFT 受 prefill 速度与排队影响；TPOT 受 decode 带宽与 batch 影响。用户先感知 TTFT。
4. 显存：KV 线性增长（4K→32K 是 8 倍）；延迟：注意力 O(n²)，明显变慢。
5. 不能。浮点非确定性 + 并行规约，只能"近似确定"。
6. 知识变更只需重建索引，不用重训；还能给引用溯源。
7. 冻结原权重，只训练 A、B 两个小矩阵（秩 r 远小于维度），可训练参数减少 99%+。
8. 吞吐上升（算力利用率提高），单请求延迟上升（要等整批）。
