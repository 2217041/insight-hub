# W2 设计记录：对话骨架与流式输出

> 目标：把 W1 的"健康检查页"换成**真正能对话的界面骨架**，并用 SSE 跑通流式。
> 后端回复目前是占位的（`_mock_answer`），W9 换成真模型时**前端一行都不用改**——这就是先定协议的价值。

## 一、这周交付了什么

| 层 | 内容 |
|---|---|
| 后端 | `POST /api/chat/stream`，SSE 流式；事件有 `start / delta / done / error` 四种 |
| 前端 | 三栏骨架：侧边栏（会话列表）+ 消息区 + 输入框 |

## 二、为什么用 SSE 而不是 WebSocket

这是 W2 的必答题。

| 维度 | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端 → 客户端） | 双向 |
| 协议 | 普通 HTTP，`text/event-stream` | 需要 `Upgrade` 握手，独立协议 |
| 断线重连 | 浏览器原生支持（`EventSource` 自动重连） | 自己实现心跳 + 重连 |
| 代理/防火墙 | 走标准 HTTPS，几乎不被拦 | 部分企业代理会掐 upgrade |
| 多路复用 | 天然支持 HTTP/2 多路复用 | 每条连接独占 |
| 实现成本 | 后端 `StreamingResponse`，前端读流 | 需要额外的服务端连接管理 |

**结论**：本项目的交互是"用户问一句 → 模型答一段"，本质是**单向推流**，SSE 足够且更简单。
只有需要"边生成边双向控制"（比如实时协作编辑、语音对讲）才值得上 WebSocket。

**注意一个坑**：原生 `EventSource` 只能发 GET、不能带请求体，所以这里用 `fetch` + `ReadableStream` 手动解析 SSE 帧，而不是 `new EventSource()`。

## 三、事件协议（前后端的契约）

```
data: {"type":"start","message_id":"...","conversation_id":"..."}
data: {"type":"delta","text":"你问的是"}
data: {"type":"delta","text":"：**测试"}
data: {"type":"done","message_id":"...","usage":{"chars":420,"elapsed_ms":2100}}
```

- 每帧以 `\n\n` 结束（SSE 规范），前端按空行切分；
- `type` 决定前端怎么处理：`delta` 追加、`done` 收尾、`error` 展示重试；
- **为什么要 `start` 帧**：让前端在正文到达前就拿到服务端的 `message_id`，方便做"按消息 id 更新"，而不是靠数组下标。

## 四、前端状态设计

```ts
Conversation { id, title, messages[], createdAt, updatedAt }
Message      { id, role, content, status: "streaming" | "done" | "error", error? }
```

三个关键决策：

1. **`status` 而不是 `isLoading` 布尔值**：一条消息可能是"完成"也可能是"失败被中断"，
   用一个枚举能同时表达空态和有内容两种流式状态，渲染逻辑也简单。
2. **流式内容直接拼进 `content`**：每来一个 delta 就更新这条消息的 `content`。
   简单直接；代价是每次都要重新渲染整个列表，消息长时会有性能问题（W13 再优化）。
3. **刷新后把 `streaming` 标记为 `error`**：页面刷新会切断流，不处理的话消息会永远卡在"生成中"。

## 五、这周要能答出来的问题

1. SSR / SSG / ISR / CSR 分别适合什么页面？本项目的对话页为什么是 CSR？
   > 对话页内容完全依赖用户本地状态与实时流，没有 SEO 与首屏内容价值，CSR + 客户端路由最合适。
2. RSC（服务端组件）相比传统 SSR 到底省了什么？
   > 省的是"组件树的 JS"——服务端组件不打包进客户端 bundle，只传序列化结果。
3. 流式输出在前端怎么实现？
   > `fetch` 拿到 `res.body`（ReadableStream）→ `getReader()` → `TextDecoder` 解码 → 按 `\n\n` 切帧 → 更新状态。
4. SSE 和 WebSocket 你怎么选？（见第二节）
5. 用户点"停止生成"时，前后端各自发生了什么？
   > 前端 `AbortController.abort()` 断开连接；后端 `await request.is_disconnected()` 返回 True 后 `return`，生成器结束。
6. 为什么不用 TanStack Query？
   > 它擅长"请求-响应"式缓存；对话是增量流，缓存模型不匹配。等 W3 做会话列表分页时再引入更合适。

## 六、当前实现里"故意先不做"的部分

| 先不做 | 为什么 | 什么时候补 |
|---|---|---|
| 登录/鉴权 | 不影响验证流式链路 | W3 |
| 数据库落库 | 建表 + 用户隔离是独立工作量 | W3/W4 |
| 真实模型 | 先把协议跑通，避免"模型慢 + 前端 bug"两个变量同时出现 | W9 |
| 多轮上下文 | 现在后端只接收单条 message | W9 |
| 消息虚拟滚动 | 消息量小的时候没必要 | W13 性能优化 |
| 代码高亮 | Markdown 已能渲染代码块，高亮是锦上添花 | 有空再加 |

重新起后端点重试 → 能正常接上。**这个场景能跑通，说明错误处理是真的做了，不是画上去的。**
