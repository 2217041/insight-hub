# W10 设计记录：解析与分块

> 一句话：**RAG 效果的上限在数据管道这里就定死了**，模型只决定下限。
> 这周没有碰模型，全部时间花在"把文档变成好块"上。

---

## 一、从 W5 到 W10 的变化

| 项 | W5（粗糙版） | W10 |
|---|---|---|
| 格式 | 只有 .md/.txt | **PDF / DOCX / MD / TXT** |
| 解析 | 按空行切段 | PDF 按栏排序 + 表格抽取；DOCX 按标题层级 |
| 分块 | 固定长度聚合 | **父子块**：父 1000 字生成，子 260 字检索 |
| 元数据 | 只有页码 | 页码 + 章节路径 + 类型（text/table/heading） |
| 顺序 | 无 | `order_index`（W12 组装上下文要用） |
| 可视化 | 无 | `/documents/{id}` 分块预览页 |

## 二、四个关键设计

### 1. 父子块（parent-child）

```
父块（~1000 字，用于喂给模型）
├─ 子块 A（~260 字，用于向量检索）
├─ 子块 B
└─ 子块 C
```

**为什么要两层**：
- 只切小块 → 检索准，但模型拿到的上下文是残片；
- 只切大块 → 上下文全，但检索噪声大、命中率低；
- 两层：**子块负责"被找到"，父块负责"被理解"**。

存储上：父块 `parent_id = NULL`，子块 `parent_id = 父块 id`。
检索时命中子块 → 按 parent_id 回填父块 → 拼进 prompt。

### 2. 表格单独成块

表格按行切开就废了（"一线 | 600" 和 "二线 | 400" 分开后，模型看不出这是同一张表）。
所以：**整张表转 Markdown，单独成一个块**，`content_type='table'`。

### 3. 父块不跨页

最初版本里 PDF 两页被合并成一个父块，结果第 2 页的内容标成了 `page=1`——
**W12 的引用溯源会因此指向错误页码**。现在遇到换页就收尾。

### 4. 顺序字段 `order_index`

同一文档内的块顺序。W12 组装上下文时要按原文顺序拼，不能按检索分数排
（否则上下文跳跃，模型理解成本上升）。

## 三、解析细节

### PDF

- `page.get_text("blocks")` 拿到带坐标的文本块；
- **先按栏、再按行排序**：`(是否右半页, y0)`。直接按 y 排会把双栏文档串行；
- `page.find_tables()` 抽表格，转 Markdown；
- 页眉页脚：多页重复的短行（出现次数 ≥ 页数一半且 < 60 字）直接删。

### DOCX

- 按 `style.name` 判断标题（`heading 1/2/3`），维护 `section_path`；
- 表格用 `doc.tables` 抽成 Markdown。

### 编码

先试 UTF-8，失败退 GBK（中文文档常见），并在日志里记一条降级提示。

## 四、实测结果

```
=== DOCX（含标题层级与表格）===
  状态=ready 子块数=4
  父块 4 / 子块 4 / 表格块 2
  章节路径: ['住宿标准', '审批流程', '差旅报销制度']
  order_index 递增: True
  [表格] '| 城市级别 | 住宿上限 |\n| 一线 | 600 |\n| 二线 | 400 |'

=== PDF（两页）===
  父块 2 / 子块 2
  [父 p1] 'Quarterly Report\n\nRevenue in Q3 reached 12.5 milli...'
  [父 p2] 'Appendix: detailed breakdown by region...'
```

页码归属正确、表格完整、章节路径保留——这三条是 W12 引用溯源的前提。

## 五、分块预览页

`/documents/{id}`：父块绿底、子块缩进，带页码/章节/token 数/表格标记。

**为什么专门做个页面**：RAG 效果差，第一大原因就是"没看过自己的块长什么样"。
切得碎不碎、有没有把表格切开、章节路径对不对——看一眼就知道，比调参数快得多。

## 九、踩的坑：脚本编辑把自己仓库的文件写坏了

**现象**：部署后线上 api 容器无限重启，日志 `sh: alembic: not found`、`No module named arq`。

**根因**：我用 PowerShell 的 `[System.IO.File]::ReadAllText/WriteAllText` 往 `requirements.txt`
追加两个依赖。第一次读文件时路径解析错了（`.NET` 用的是进程工作目录，不是 PowerShell 的 `cd`），
`$r` 变成 `null`，后续的 `WriteAllText` 就把文件写成了只剩追加的两行——
**原来的 14 个依赖全丢了**。

**为什么没早发现**：脚本没报错、`Get-Content` 只看末尾几行（正好是新加的那两行），
而本地 venv 早就装好了依赖，所以本地跑得好好的。**直到线上容器启动失败才暴露。**

**修复**：`git show <之前的提交>:apps/api/requirements.txt` 取回原文件，再补两个新依赖。

**三条教训**：
1. **用 .NET API 读写文件必须用绝对路径**（`cd` 不影响 .NET 的当前目录）；
2. **脚本改完文件要立刻验证内容**（`Get-Content` 全量读一次，或比对行数），不能只看末尾；
3. **本地 venv 能跑 ≠ 镜像能跑**。依赖清单的验证方式是"重建镜像 + 起容器"，
   而这一步本该在推送前做。

> 这次事故的代价：线上 502 约 15 分钟，多传了 250 MB 镜像。

## 十、另一个坑：pymupdf 2.x 体积翻倍

`pymupdf>=1.24` 解析到了 2.1，会连带装 `pymupdf-layout` + `onnxruntime`，
镜像从 321 MB 涨到 619 MB——只为了 PDF 版面分析。

处理：锁 `pymupdf>=1.24,<2`，镜像回到 440 MB。**能用小版本解决就别升大版本。**
