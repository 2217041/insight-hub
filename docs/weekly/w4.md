## 四、五个卡点

### 1. `DROP SCHEMA` 看着执行了，其实全回滚了

- **现象**：清库命令打印了 `DROP SCHEMA`、`CREATE SCHEMA`，但后面一查表还在。
- **原因**：`psql -c 'A; B; C;'` 是**一个事务**，最后一条 `CREATE EXTENSION vector` 因为权限不足失败，
  导致前面两条一起回滚。psql 是逐条打印 tag 的，所以看起来像成功了。
- **教训**：**多语句要么分开执行，要么用 `-f` 脚本文件并加 `-v ON_ERROR_STOP=1`**。

### 2. 扩展被普通用户删了之后建不回来

- `DROP SCHEMA public CASCADE` 把 pgvector 扩展一起删了，
  而 `insight` 不是超级用户，`CREATE EXTENSION` 直接 permission denied。
- **处理**：用 `postgres` 超级用户重建，并 `GRANT ALL ON SCHEMA public TO insight`。

### 3. `default=True` 对原生 SQL 不生效

- **现象**：造数脚本插入 `users` 报 `null value in column "is_active"`。
- **原因**：`default=True` / `default=list` 是 **SQLAlchemy 在 Python 侧**填的，
  绕过 ORM 直接写 SQL 就不会有值。
- **教训**：多环境共用一张表时，重要默认值应该用 `server_default`（数据库层兜底）。

### 4. 改表把注册接口打断了

- **现象**：加完 `tenant_id NOT NULL` 后，注册直接 500。
- **原因**：注册逻辑只建用户，不建租户。
- **处理**：注册即创建个人租户，两个 INSERT 放同一事务（`commit=False` + 统一 commit）。
- **教训**：**迁移的验收标准不是"表建对了"，而是"业务还能跑"**。这条以后每周都要做回归。

### 5. 500 响应里的 request_id 是 `-`

- **现象**：注册失败时错误体是 `{"code":"INTERNAL_500","request_id":"-"}`，线上没法定位。
- **原因**：我在中间件 `finally` 里 reset 了 contextvar，而全局异常处理器运行在中间件**之外**，读不到值。
- **处理**：异常路径不 reset。
- **教训**：**只在出错时才会暴露的问题，正常流程永远测不出来**。这次纯属运气好。

## 五、技术收获

1. **索引解决"定位"，不解决"扫描量"**。
   深分页 `OFFSET 100000` 加索引只快 4.3 倍（仍 18 ms），而 Keyset 只要 0.022 ms——差 800 倍。
2. **低选择性列不该建索引**。`role` 只有两个值，加了索引反而慢 0.8 ms。
3. **复合索引的第一列决定一切**。`(tenant_id, created_at)` 对"全局最近消息"完全没用。
4. **RLS 的 `FORCE` 是必须的**，否则表 owner 绕过策略，配了等于没配。
5. **`SET LOCAL` 而不是 `SET`**：会话级设置会在连接池复用时串租户。

## 六、方法收获

1. **实验要有对照组，而且对照组要真的"没有那个东西"**。
   用 `enable_indexscan=off` 模拟"没索引"是假的，我选择了真删真建。
2. **危险实验要能自动恢复**。bench 脚本最后调 `ensure_schema()`，把索引恢复到与迁移一致，
   并打印每表索引数——避免留下"少了个索引"的脏状态。
3. **改完结构必须跑业务回归**。这次就是靠"注册 500"发现的。
