## 三、卡点

### 1. 父块跨页导致页码全错（自己测出来的）

最初 PDF 两页被合进一个父块，第 2 页的内容标成 `page=1`。
**这会让 W12 的引用溯源指到错误页码。** 改法：换页就收尾，父块不跨页。

> 这个 bug 不会报错，只有把块打出来看才发现——所以**分块预览页不是"锦上添花"**。

### 2. 我把自己仓库的 requirements.txt 写坏了（事故）

- **现象**：线上 api 容器无限重启，`sh: alembic: not found`。
- **根因**：用 PowerShell 的 `.NET API` 追依赖，第一次 `ReadAllText` 因**相对路径**解析失败返回 `null`
  （.NET 用的是进程工作目录，不是 PowerShell 的 `cd`），随后的写入把文件覆盖成只剩两行。
- **为什么没早发现**：脚本没报错、`Get-Content` 只看末尾（正好是新加的两行）、本地 venv 早就装好依赖。
- **代价**：线上 502 约 15 分钟，多传 250 MB 镜像。
- **修复**：`git show <commit>:apps/api/requirements.txt` 取回，再补新依赖。

**三条教训**：
1. `.NET` 文件 API 必须用绝对路径；
2. 脚本改完要**全量**校验（行数/全文），不能只看末尾；
3. **本地能跑 ≠ 镜像能跑**，依赖清单的验证标准是"重建镜像 + 起容器"。

### 3. pymupdf 2.x 体积翻倍

`>=1.24` 解析到 2.1，连带 `onnxruntime`，镜像 321 MB → 619 MB。锁 `<2` 后回到 440 MB。

## 四、技术收获

1. **双栏 PDF 不能直接按 y 排序**，要先判左右栏再排序，否则两栏内容会串行。
2. **表格必须整体成块**（转 Markdown），按行切会毁掉语义——"一线|600"和"二线|400"分开就不是一张表了。
3. **父子块是 RAG 的标配**：子块负责被找到，父块负责被理解。
4. **`order_index` 必须显式存**，否则"按检索分数排"会让上下文跳跃。

---

## 五、方法收获

1. **造真实测试文件验证**，不要用假字符串——python-docx / pymupdf 各造一份，跑同一条链路。
2. **分块预览是调试 RAG 的第一现场**：切碎了、表格坏了、页码错了，肉眼一秒就能看出来。
3. **镜像体积要盯**：一个依赖的大版本可能让镜像翻倍。
